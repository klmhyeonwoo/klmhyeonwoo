## AI 에이전트가 늘어날수록 무엇이 불편해질까?

Claude Code나 Codex 같은 코딩 에이전트를 사용하다 보면, 하나의 작업이 끝나기를 기다리는 시간이 아쉽게 느껴질 때가 있다. 기능을 구현하는 동안 테스트 코드를 작성하거나, 다른 에이전트에게 별도의 버그 수정을 맡기고 싶어지기 때문이다.

하지만 에이전트를 여러 개 띄우는 순간 새로운 문제가 생긴다. 터미널 창이 늘어나면 어떤 에이전트가 무슨 작업을 하고 있는지 파악하기 어렵다. 같은 프로젝트 폴더에서 동시에 작업하면 한 에이전트가 수정 중인 파일을 다른 에이전트가 덮어쓸 수도 있다.

각 작업을 별도의 브랜치와 폴더로 나누면 어느 정도 해결할 수 있다. 다만 작업 공간을 만들고, 에이전트를 실행하고, 결과를 비교하는 과정을 매번 직접 관리해야 한다. **Orca는 이런 과정을 하나의 화면에서 관리할 수 있도록 만든 에이전트 개발 환경이다.**

## Orca는 어떤 도구일까?

Orca는 새로운 AI 모델이 아니다. Claude Code, Codex, Gemini CLI처럼 이미 사용하고 있는 코딩 에이전트를 실행하고 관리하는 데 초점을 맞춘 오픈소스 데스크톱 도구다.

개발자가 에디터에서 코드를 직접 작성하는 데 집중하는 환경과 달리, Orca가 제안하는 환경에서는 여러 에이전트에게 작업을 나누어 맡기고 그 결과를 확인하는 과정이 중요해진다. Orca는 이를 ADE, Agent Development Environment라고 부른다.

물론 ADE와 IDE가 완전히 다른 도구라는 뜻은 아니다. Orca 역시 편집기, 터미널, 변경 사항 비교 화면을 제공한다. 차이는 코드를 직접 작성하는 공간뿐 아니라 **여러 에이전트의 작업 공간과 진행 상황을 함께 관리하는 데 무게를 둔다**는 점이다.

Orca는 여러 CLI 에이전트를 지원하지만, 에이전트마다 상태 표시나 사용량 확인처럼 깊게 연동되는 기능에는 차이가 있다. 사용할 에이전트의 설치와 로그인, 이용 요금도 별도로 확인해야 한다.

## Git worktree로 작업 공간을 나누는 이유

내가 Orca에서 특히 유용하다고 느낀 부분은 Git worktree를 기반으로 작업 공간을 분리한다는 점이다.

Git worktree는 하나의 Git 저장소에서 여러 작업 디렉터리를 만들어 각각 다른 브랜치를 체크아웃할 수 있는 기능이다. 저장소를 매번 새로 복제하지 않고도 작업별로 분리된 파일 공간을 가질 수 있다.

예를 들어 다음과 같이 작업을 나눌 수 있다.

- 메인 작업 공간: 내가 새로운 기능을 직접 구현한다.
- 작업 공간 A: 에이전트에게 로그인 버그 수정을 맡긴다.
- 작업 공간 B: 다른 에이전트에게 기존 기능의 테스트 코드 작성을 맡긴다.

각 작업이 별도의 worktree에서 진행되면 한쪽에서 파일을 수정하더라도 다른 작업 공간의 파일을 직접 건드리지 않는다. 브랜치를 바꾸기 위해 현재 변경 사항을 임시 저장하는 과정도 줄일 수 있다.

Orca에서는 작업별 worktree와 브랜치, 에이전트 터미널을 연결해 관리한다. 작업이 끝나면 변경 사항을 비교하는 Diff 화면에서 결과를 확인한 뒤 필요한 내용을 병합할 수 있다.

## 병렬 실행과 오케스트레이션은 어떻게 다를까?

멀티 에이전트 도구를 이야기할 때 병렬 실행과 오케스트레이션이 자주 함께 등장한다. 둘은 관련이 있지만 같은 뜻은 아니다.

### 병렬 실행: 여러 작업을 동시에 진행한다

병렬 실행은 여러 에이전트에게 각각 작업을 맡기고 동시에 실행하는 방식이다. 예를 들어 한 에이전트는 로그인 버그를 수정하고, 다른 에이전트는 결제 페이지 UI를 만들고, 또 다른 에이전트는 테스트 코드를 작성할 수 있다.

이때 작업을 어떻게 나눌지 결정하고 결과를 합치는 역할은 개발자가 직접 맡을 수도 있다. 중요한 것은 작업이 동시에 진행된다는 점이다.

다만 에이전트를 많이 띄운다고 무조건 빨라지는 것은 아니다. 작업 간 의존성이 높거나 같은 파일을 자주 수정하면 결과를 검토하고 병합하는 데 오히려 더 많은 시간이 들 수 있다.

### 오케스트레이션: 작업의 순서와 관계까지 조율한다

오케스트레이션은 여러 작업의 역할, 순서, 의존 관계, 결과 전달 방식까지 조율하는 개념이다. 예를 들어 새로운 결제 기능을 만든다고 해보자.

1. 먼저 API 요구 사항과 데이터 형식을 정리한다.
2. 정리된 내용을 바탕으로 백엔드와 프론트엔드 작업을 나눈다.
3. 각 작업이 끝나면 변경 사항을 검토하고 연결한다.
4. 마지막으로 전체 흐름을 테스트한다.

이 과정에서는 무작정 동시에 실행하는 것보다 어떤 작업이 먼저 끝나야 하는지와 결과를 다음 작업에 어떻게 전달할지가 중요하다.

Orca는 여러 에이전트를 한 화면에서 실행하는 것뿐 아니라 에이전트가 작업자를 만들고 조율할 수 있는 기능도 제공한다. 다만 도구가 에이전트를 실행해준다는 것과 모든 작업이 자동으로 올바르게 연결된다는 것은 다르다. 작업 경계와 결과 검토는 여전히 신경 써야 한다.

## Orca에서 실제로 작업을 시작하는 방법

Orca에서의 기본 흐름은 저장소를 연결하고, 작업별 worktree를 만든 뒤, 그 안에서 에이전트를 실행하는 것이다.

1. 프로젝트를 추가하고 Git 저장소를 선택한다.
2. 저장소 옆의 + 버튼으로 작업 이름과 기준 브랜치를 지정해 worktree를 만든다.
3. 워크스페이스에서 Claude Code나 Codex 등 사용할 에이전트를 선택하고 작업을 요청한다.
4. 작업이 끝나면 Diff를 확인하고 필요한 수정 사항을 전달한다.
5. 결과가 준비되면 Orca 안에서 커밋하고 푸시한다.

같은 작업을 여러 방식으로 풀어보고 싶다면 같은 기준 브랜치에서 worktree를 여러 개 만든 뒤 동일한 프롬프트를 각각 전달할 수도 있다. 화면을 분할해 진행 상황을 나란히 보고, 결과물의 Diff를 비교해 원하는 접근 방식을 선택하는 것이다.

## Diff에 직접 코멘트하고 에이전트에게 다시 전달하기

코드 리뷰 과정에서 변경된 줄을 복사하거나 파일 경로와 줄 번호를 일일이 설명할 필요도 줄일 수 있다. Orca의 **Annotate AI Diff**에서는 에이전트가 변경한 코드의 특정 줄이나 여러 줄을 선택해 코멘트를 남기고, 코멘트들을 한 번에 에이전트에게 전달할 수 있다.

예를 들어 로그인 예외 처리 부분에 “이 분기는 서버 오류와 인증 실패를 구분해줘”라고 남기면 해당 코드 위치와 함께 피드백을 전달하는 식이다. Diff 화면에서는 스테이징된 변경과 아직 스테이징하지 않은 변경, 새 파일을 함께 살펴볼 수 있고, 변경된 일부 구간이나 줄만 선택해 스테이징하는 기능도 제공한다.

## 작업별 브라우저에서 화면을 확인하고 수정 요청하기

Orca의 내장 브라우저는 단순한 미리보기 창이 아니다. 각 worktree에 연결된 Chromium 브라우저로, 작업 공간을 전환할 때 해당 작업의 브라우저 탭으로 다시 돌아갈 수 있다. 개발자 도구를 열거나 화면 크기를 지정해 반응형 레이아웃을 살펴보는 것도 가능하다.

Design Mode와 Annotate 기능을 활용하면 화면 요소를 집어 HTML과 스타일, 선택자 같은 정보를 가져오거나 화면에 표시한 내용을 바탕으로 수정 요청을 전달할 수 있다. 에이전트가 Orca CLI로 같은 브라우저의 페이지를 살펴보고 조작하는 방식도 지원한다. 프론트엔드 작업에서 코드, 실행 화면, 에이전트 대화를 오가는 흐름을 한 작업 공간에 모아둘 수 있는 셈이다.

## 조정자와 작업자로 나누는 오케스트레이션

Orca에는 여러 에이전트의 작업을 구조화해 관리하는 오케스트레이션 기능도 있다. 여기서 **Run**은 전체 작업의 범위와 메시지를 모으는 공간이고, **Task**는 명세와 의존 관계, 상태를 가진 개별 작업이다. 실제 작업을 작업자에게 맡기는 한 번의 시도는 **Dispatch**로 구분한다.

예를 들어 결제 기능 개선을 맡긴다면 조정자가 화면 점검과 테스트 코드 작성을 각각 Task로 나누고, 작업자에게 할당한 뒤 완료 결과를 받아볼 수 있다. 각 작업은 대기, 진행, 완료, 실패, 차단 등의 상태로 관리된다. 작업자가 판단이 필요한 질문을 보내거나, 특정 결정이 내려질 때까지 후속 작업을 막는 Decision gate도 제공한다.

작업자마다 같은 worktree를 사용하거나 새 작업 공간을 만들어 실행할 수 있다. 즉 단순히 터미널을 여러 개 켜두는 것에서 나아가, 어떤 작업을 누구에게 맡겼고 무엇이 끝났는지 추적할 수 있도록 구성한 것이다.

## 로컬을 넘어 SSH와 원격 서버에서 실행하기

Orca는 내 노트북에서만 에이전트를 실행하는 도구도 아니다. SSH 대상을 연결하면 worktree와 에이전트는 원격 머신에서 실행하고, 노트북의 Orca에서는 편집기와 Diff 등 인터페이스를 이용할 수 있다. 이미 개발 환경을 갖춘 서버에서 작업을 수행하면서 화면은 익숙한 데스크톱 앱으로 보는 방식이다.

**Remote Orca Server**는 이와 조금 다르다. 원격 컴퓨터가 프로젝트, worktree, 터미널과 에이전트 세션을 보유하고, 노트북이나 다른 클라이언트가 해당 실행 환경에 연결한다. 서버가 계속 실행 중이라면 노트북 연결이 끊겨도 서버의 에이전트 작업은 이어질 수 있다. 공식 문서는 이 기능을 베타로 안내한다.

이 밖에도 저장소의 설정을 이용해 worktree별 클라우드 VM이나 로컬 컨테이너 환경을 준비하는 방식을 제공한다. 작업을 실행할 위치에 따라 로컬, SSH, 원격 서버 중에서 고를 수 있다는 점이 특징이다.

## 반복 작업을 맡기는 Orca Bots

Orca에는 한 번 실행하고 끝나는 코딩 에이전트 외에 이름과 역할, 메모리, 자동화를 가진 **Bot**도 있다. 채팅에서 직접 작업을 요청하거나 일정을 지정할 수 있고, 연결 설정을 마치면 Slack, GitHub, Linear에서 작업을 받아 요청한 곳으로 결과를 돌려줄 수 있다.

예를 들어 매일 아침 저장소의 변경 사항과 검토할 내용을 요약하거나, PR에서 CI가 실패했을 때 원인을 살펴보도록 맡길 수 있다. 코드 변경이 필요한 작업은 별도의 worktree에서 실행되는 작업자에게 넘기고, 봇은 그 결과를 받아 전달하는 구조다. 사용자의 결정이나 승인이 필요한 항목은 Bot의 Home에 모여 기다린다.

이 기능을 사용하면 Orca를 여러 터미널을 정리하는 앱뿐 아니라, 반복되는 개발 업무를 에이전트와 연결하는 작업 공간으로도 활용할 수 있다.

## 글을 마치며

Orca가 모든 개발자에게 필요한 도구는 아니다. 에이전트 하나로 작업하고 있고 현재 사용하는 앱에서 충분히 진행 상황을 확인할 수 있다면 새로운 도구를 추가할 이유가 크지 않을 수 있다.

반면 기능을 직접 구현하면서 테스트나 버그 수정을 별도로 맡기고 싶거나, 여러 에이전트에게 같은 문제를 맡긴 뒤 결과를 비교하고 싶다면 한 번 살펴볼 만하다. worktree와 브랜치를 매번 직접 관리하는 과정이 번거로운 경우에도 도움이 될 수 있다.

내게 Orca가 흥미로운 이유도 여기에 있다. AI 에이전트가 코드를 얼마나 잘 작성하는지만큼, 여러 작업을 어떻게 나누고 결과를 어떻게 검토할 것인지가 점점 중요해지고 있기 때문이다.

Orca는 그 과정을 대신 판단해주는 도구라기보다는 개발자가 여러 에이전트의 작업을 더 편하게 관리하고 확인할 수 있도록 돕는 작업 공간에 가깝다. 병렬 작업이 필요한 순간이 자주 찾아온다면 기존 개발 환경과 비교해 볼 만한 선택지다.

Claude Code나 Codex 같은 코딩 에이전트를 사용하다 보면, 하나의 작업이 끝나기를 기다리는 시간이 아쉽게 느껴질 때가 있다. 기능을 구현하는 동안 테스트 코드를 작성하거나, 다른 에이전트에게 별도의 버그 수정을 맡기고 싶어지기 때문이다.

하지만 에이전트를 여러 개 띄우는 순간 새로운 문제가 생긴다. 터미널 창이 늘어나면 어떤 에이전트가 무슨 작업을 하고 있는지 파악하기 어렵다. 같은 프로젝트 폴더에서 동시에 작업하면 한 에이전트가 수정 중인 파일을 다른 에이전트가 덮어쓸 수도 있다.

각 작업을 별도의 브랜치와 폴더로 나누면 어느 정도 해결할 수 있다. 다만 작업 공간을 만들고, 에이전트를 실행하고, 결과를 비교하는 과정을 매번 직접 관리해야 한다. **Orca는 이런 과정을 하나의 화면에서 관리할 수 있도록 만든 에이전트 개발 환경이다.**

## Orca는 어떤 도구일까?

Orca는 새로운 AI 모델이 아니다. Claude Code, Codex, Gemini CLI처럼 이미 사용하고 있는 코딩 에이전트를 실행하고 관리하는 데 초점을 맞춘 오픈소스 데스크톱 도구다.

개발자가 에디터에서 코드를 직접 작성하는 데 집중하는 환경과 달리, Orca가 제안하는 환경에서는 여러 에이전트에게 작업을 나누어 맡기고 그 결과를 확인하는 과정이 중요해진다. Orca는 이를 ADE, Agent Development Environment라고 부른다.

물론 ADE와 IDE가 완전히 다른 도구라는 뜻은 아니다. Orca 역시 편집기, 터미널, 변경 사항 비교 화면을 제공한다. 차이는 코드를 직접 작성하는 공간뿐 아니라 **여러 에이전트의 작업 공간과 진행 상황을 함께 관리하는 데 무게를 둔다**는 점이다.

Orca는 여러 CLI 에이전트를 지원하지만, 에이전트마다 상태 표시나 사용량 확인처럼 깊게 연동되는 기능에는 차이가 있다. 사용할 에이전트의 설치와 로그인, 이용 요금도 별도로 확인해야 한다.

## Git worktree로 작업 공간을 나누는 이유

내가 Orca에서 특히 유용하다고 느낀 부분은 Git worktree를 기반으로 작업 공간을 분리한다는 점이다.

Git worktree는 하나의 Git 저장소에서 여러 작업 디렉터리를 만들어 각각 다른 브랜치를 체크아웃할 수 있는 기능이다. 저장소를 매번 새로 복제하지 않고도 작업별로 분리된 파일 공간을 가질 수 있다.

예를 들어 다음과 같이 작업을 나눌 수 있다.

- 메인 작업 공간: 내가 새로운 기능을 직접 구현한다.
- 작업 공간 A: 에이전트에게 로그인 버그 수정을 맡긴다.
- 작업 공간 B: 다른 에이전트에게 기존 기능의 테스트 코드 작성을 맡긴다.

각 작업이 별도의 worktree에서 진행되면 한쪽에서 파일을 수정하더라도 다른 작업 공간의 파일을 직접 건드리지 않는다. 브랜치를 바꾸기 위해 현재 변경 사항을 임시 저장하는 과정도 줄일 수 있다.

Orca에서는 작업별 worktree와 브랜치, 에이전트 터미널을 연결해 관리한다. 작업이 끝나면 변경 사항을 비교하는 Diff 화면에서 결과를 확인한 뒤 필요한 내용을 병합할 수 있다.

### 그렇다고 충돌이 완전히 사라지는 것은 아니다

Worktree가 분리하는 것은 작업 중인 파일 공간이다. 서로 다른 브랜치에서 같은 코드를 수정했다면 나중에 병합할 때 충돌할 수 있다.

또한 로컬 서버 포트, 데이터베이스, 외부 API, 환경 변수처럼 worktree 밖에서 공유하는 자원까지 자동으로 격리되는 것은 아니다. 두 에이전트가 같은 포트로 개발 서버를 실행하거나 같은 데이터베이스를 수정하지 않도록 따로 확인해야 한다.

따라서 병렬 작업을 맡길 때는 가능하면 수정할 영역과 완료 조건을 나누는 편이 좋다. 예를 들어 한 에이전트에게는 로그인 화면의 유효성 검사 수정을, 다른 에이전트에게는 로그인 API 테스트 코드 작성을 맡길 수 있다. 인증 관련 설정 파일처럼 공통으로 건드릴 수 있는 부분은 수정 전에 알려달라는 조건을 함께 적어두는 방법도 있다.

## 병렬 실행과 오케스트레이션은 어떻게 다를까?

멀티 에이전트 도구를 이야기할 때 병렬 실행과 오케스트레이션이 자주 함께 등장한다. 둘은 관련이 있지만 같은 뜻은 아니다.

### 병렬 실행: 여러 작업을 동시에 진행한다

병렬 실행은 여러 에이전트에게 각각 작업을 맡기고 동시에 실행하는 방식이다. 예를 들어 한 에이전트는 로그인 버그를 수정하고, 다른 에이전트는 결제 페이지 UI를 만들고, 또 다른 에이전트는 테스트 코드를 작성할 수 있다.

이때 작업을 어떻게 나눌지 결정하고 결과를 합치는 역할은 개발자가 직접 맡을 수도 있다. 중요한 것은 작업이 동시에 진행된다는 점이다.

다만 에이전트를 많이 띄운다고 무조건 빨라지는 것은 아니다. 작업 간 의존성이 높거나 같은 파일을 자주 수정하면 결과를 검토하고 병합하는 데 오히려 더 많은 시간이 들 수 있다.

### 오케스트레이션: 작업의 순서와 관계까지 조율한다

오케스트레이션은 여러 작업의 역할, 순서, 의존 관계, 결과 전달 방식까지 조율하는 개념이다. 예를 들어 새로운 결제 기능을 만든다고 해보자.

1. 먼저 API 요구 사항과 데이터 형식을 정리한다.
2. 정리된 내용을 바탕으로 백엔드와 프론트엔드 작업을 나눈다.
3. 각 작업이 끝나면 변경 사항을 검토하고 연결한다.
4. 마지막으로 전체 흐름을 테스트한다.

이 과정에서는 무작정 동시에 실행하는 것보다 어떤 작업이 먼저 끝나야 하는지와 결과를 다음 작업에 어떻게 전달할지가 중요하다.

Orca는 여러 에이전트를 한 화면에서 실행하는 것뿐 아니라 에이전트가 작업자를 만들고 조율할 수 있는 기능도 제공한다. 다만 도구가 에이전트를 실행해준다는 것과 모든 작업이 자동으로 올바르게 연결된다는 것은 다르다. 작업 경계와 결과 검토는 여전히 신경 써야 한다.

## 브라우저와 Diff를 함께 보는 작업 방식

에이전트에게 코드를 맡긴 뒤에는 결과를 확인하는 과정이 필요하다. Orca는 이를 위해 터미널뿐 아니라 브라우저와 Diff 화면을 작업 공간 안에 함께 배치할 수 있도록 한다.

예를 들어 UI 수정 작업이라면 에이전트에게 수정을 요청한 뒤 내장 브라우저에서 실행 중인 화면을 확인할 수 있다. 수정이 필요한 요소를 선택해 관련 정보를 에이전트에게 전달하고, 수정 결과와 코드 변경 범위를 다시 확인하는 식이다.

Orca의 Design Mode에서는 브라우저의 요소를 클릭해 HTML, 스타일, 선택자 정보를 복사하고 에이전트 대화에 전달할 수 있다. 화면을 보며 수정 위치를 설명하기 어려울 때 활용할 만한 기능이다.

화면이 원하는 대로 바뀌었다고 해서 검토가 끝나는 것은 아니다. 의도하지 않은 파일 수정은 없는지, 기존 동작은 유지되는지, 테스트가 필요한 부분은 없는지 코드도 함께 살펴봐야 한다.

## 사용하기 전에 확인할 점

### 1. 에이전트의 실행 권한을 살펴보자

Worktree가 분리되어 있다고 해서 에이전트가 컴퓨터 전체에서 완전히 격리되는 것은 아니다. 에이전트가 가진 권한에 따라 셸 명령을 실행하거나 공유 자원에 접근할 수 있기 때문이다.

특히 Orca 공식 문서에는 새 에이전트를 실행할 때 지원되는 CLI의 권한 확인 우회 옵션을 미리 채워 넣는다고 안내되어 있다. 기본으로 채워지는 옵션은 에이전트마다 다르다. 민감한 파일이나 운영 환경에 접근할 수 있는 작업이라면 실행 전에 옵션을 확인하고 필요한 수준으로 권한을 조정하는 것이 좋다.

### 2. 병렬 작업의 비용과 사용량을 고려하자

여러 에이전트를 동시에 실행하면 그만큼 모델 사용량도 늘어날 수 있다. 같은 문제를 여러 에이전트에게 풀게 하는 방식은 결과를 비교하기 좋지만, 작업 성격에 따라 비용 대비 효용이 낮을 수도 있다.

처음에는 서로 독립적인 두 작업 정도로 시작해 보고, 결과를 검토하는 데 드는 시간까지 포함해 자신에게 맞는 작업 방식을 찾는 것이 좋다.

### 3. 개발 환경이 worktree마다 준비되어 있는지 확인하자

새 worktree에는 브랜치의 추적 파일이 준비되지만, 무시된 환경 변수 파일이나 설치된 의존성처럼 별도로 관리되는 항목은 기존 작업 공간과 다를 수 있다.

실행이 되지 않는다면 코드부터 수정하기보다 환경 변수, 패키지 설치, 개발 서버 포트, 테스트용 데이터베이스 설정을 먼저 확인해 보는 편이 좋다. 민감한 설정 파일은 무심코 복사하거나 에이전트에게 노출하지 않도록 주의해야 한다.

## 글을 마치며

Orca가 모든 개발자에게 필요한 도구는 아니다. 에이전트 하나로 작업하고 있고 현재 사용하는 앱에서 충분히 진행 상황을 확인할 수 있다면 새로운 도구를 추가할 이유가 크지 않을 수 있다.

반면 기능을 직접 구현하면서 테스트나 버그 수정을 별도로 맡기고 싶거나, 여러 에이전트에게 같은 문제를 맡긴 뒤 결과를 비교하고 싶다면 한 번 살펴볼 만하다. worktree와 브랜치를 매번 직접 관리하는 과정이 번거로운 경우에도 도움이 될 수 있다.

내게 Orca가 흥미로운 이유도 여기에 있다. AI 에이전트가 코드를 얼마나 잘 작성하는지만큼, 여러 작업을 어떻게 나누고 결과를 어떻게 검토할 것인지가 점점 중요해지고 있기 때문이다.

Orca는 그 과정을 대신 판단해주는 도구라기보다는 개발자가 여러 에이전트의 작업을 더 편하게 관리하고 확인할 수 있도록 돕는 작업 공간에 가깝다. 병렬 작업이 필요한 순간이 자주 찾아온다면 기존 개발 환경과 비교해 볼 만한 선택지다.
