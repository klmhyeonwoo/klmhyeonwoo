공통 ` ListBox ` 컴포넌트에 API로 받아온 사용처 목록을 전달하려고 헀을 때, 고쳐지지 않는 타입 오류가 있었다.

```typescript
<ListBox
	:items="data ?? []"
	item-title="codeName"
	item-value="codeId"
/>
```

` data `는 API가 반환한 배열이다. 아직 데이터를 받지 못했다면 ` items ` props 안으로 빈 배열을 넘긴다.

```typescript
const data = [
	{ codeId: 'TIGL01', codeName: '보고서' },
	{ codeId: 'TIGL02', codeName: '위협 분석'}
]
```

분명 배열을 넘겼는데, ` items `에 타입 오류가 표시됐다. 원인은 배열이 아니라 배열 안에 들어있는 객체의 타입에 존재했다.

## ` ListBox ` 컴포넌트가 원하는 타입

공통 ` ListBox `는 다양한 데이터를 받을 수 있도록 항목의 타입을 이렇게 정의하고 있다.

```typescript
type Item = {
	[key: string]: string | number | boolean | null
}

type Props = {
	items: readonly Item[];
}
```

` [key: string] `은 문자열로 된 키를 사용하고, 그 값은 지정된 타입 중 하나인 객체를 뜻한다. 이런 선언을 인덱스 시그니처라고 하는데, 예를 들면 ` ListBox ` 컴포넌트는 아래와 같이 데이터를 받을 수 있다.

```typescript
const items: Item[] = [
	{ codeId: 'TIGL01', codeName: '보고서' },
	{ codeId: 'TIGL02', codeName: '위협 분석' }
]
```

## API의 데이터 타입

API가 반환하는 항목은 아래와 같이 ` interface `로 정의되어있었다.

```typescript
interface GuidelineCode {
	codeId: string;
	codeName: string;
}
```

겉으로 보면 두 속성 모두 문자열이니 ` Item `에 타입이 잘 대입이 될 것 같지만, 타입스크립트에서 이를 할당하면 오류가 발생한다.

```typescript
declare const guideline: GuidelineCode;

const item: Item = guideline;
// error : GuidelineCode에 문자열 인덱스 시그니처가 없음
```

` GuidelineCode `는 ` codeId `와 ` codeName `이 있다는 것은 알려주지만,`  Item `처럼 다른 문자열 키로 접근할 때 값이 어떤 타입인지는 선언하지 않았기 때문이다.

## interface를 type으로 바꾸었을 때

같은 모양을 객체 타입 별칭으로 선언하면 할당이 가능하다.

```typescript
type Guidelinecode = {
	codeId: string;
	codeName: string;
}

declare const guideline: GuidelineCode;

const item: Item = guideline // ok
```

타입스크립트는 이 객체 타입 별칭을 ` Item `에 할당할 때, 알려진 속성의 값들이 ` Item `에서 허용하는 타입인지 확인한다. ` codeId `와 ` codeName `이 모두 ` string `이므로 통과한다. 반면 ` interface `는 나중에 같은 이름으로 선언을 추가하는 선언 병합이 가능하다. 타입스크립트는 이런 **인터페이스에 대해 인덱스 시그니처를 암묵적으로 추론**하지 않는다.

```typescript
interface GuidelineCode {
	codeId: string;
}

interface GuidelineCode {
	codeName: string;
}

// 두 선언이 합쳐져 codeId와 codeName을 모두 가짐
```

여기서 주의할 점은, ` type `으로 바꿨다고 ` GuidelineCode `에 인덱스 시그니처가 실제로 생기는 것은 아니라는 것이다. 알려지지 않은 키에 마음대로 접근할 수 있는게 아니라 ` Item `에 할당할 떄 타입스크립트의 호환성 판단이 달라지는 것이다.

## &\#123; ...item &\#125; 은 타입 통과를 한다

같은 응답을 넘기지만, 복사를 하여 전달을 하게되면 타입이 통과하는 신기한 현상이 있다.

```typescript
return response.data.map((item) => ({ ...item ));
```

이 코드는 각 항목을 새로운 객체로 만든다. 타입스크립트도 결과를 ` GuidelineCode ` 인터페이스가 아닌 새로운 객체 리터럴 타입으로 추론하기 때문에 알려진 속성들을 검사한 뒤 ` Item `에 할당할 수 있다. 하지만 데이터가 바뀌는 것은 아니라 타입 오류만 해결하려고 객체를 복사하는 것은 불필요한 작업이 될 수 있다.

처음에는 Vue의 반응성 문제로 인해 타입스크립트에서 오류를 띄우는 것은 아닌지 의심을 해보았지만, 정의해놓은 API 항목 타입과 ` ListBox ` 컴포넌트가 요구하는 항목 타입 사이의 호환성 문제였다. 객체 타입 별칭은 인덱스 시그니처를 가진 타입에 할당할 때, 알려진 속성들이 해당 인덱스 시그니처와 호환되면 할당이 허용된다.

```typescript
code['없는 키']; // 임의의 키 접근이 허용되는 것은 아니다.
```

이를 암묵적 인덱스 시그니처라고 설명하지만, 원본 타입에 임의의 키 접근이 가능해지는 것은 아니다. ` type `을 사용할 때 인덱스 시그니처를 암묵적으로 추론하여 이렇게 타입 오류를 피한다는 것은 처음 알게될 수 있었다.
