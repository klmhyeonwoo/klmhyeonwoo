`IndexedDB`는 기술 면접을 준비할 때 브라우저의 로컬 저장소에 관련된 내용들을 배우면서, 한번쯔음 들어보았을 용어이다. 사실 쿠키를 많이 사용해보았지, `IndexedDB`의 경우에는 사용할 일이 많이 없다고 생각해 실제로 써보지는 못했는데 이번에 게시글 자동저장 기능을 구현해보면서 여러 로컬 저장소들과의 특징들을 비교하며 도입을 하고자했다.

객체 형태의 저장 형태 · 대용량 저장소 · 비동기 처리 등의 특징과 메인 스레드를 블로킹하지 않는 특성들이 `IndexedDB`가 자동 저장에 적합하다고 생각이 들었다. 오늘은 `IndexedDB` 를 활용해보며 배웠던 내용들을 복기차 포스팅을 해보려고 한다.

## IndexedDB란?

브라우저에 내장된 비동기 NoSQL 데이터베이스로, 대용량 및 구조화된 데이터를 영구적으로 저장할 수 있는 클라이언트 DB이다. `IndexedDB`는 웹이 단순 문서에서 오프라인 및 대용량 데이터를 다루는 어플리케이션으로 진화하면서, 기존 저장소(Local Stoarge, Cookie)가 이러한 요구 조건들을 감당하지 못해 등장하게 되었다.

### 초창기 웹 저장소의 한계점

우리가 흔히 알고 있는 `Cookie` 와 `LocalStorage` 와 같은 로컬 스토리지의 경우에는 아래와 같은 한계점을 가지고 있었다.

**Cookie**

* 4KB의 용량을 가진다.

* 모든 요청마다 서버로 전송된다.

**LocalStorage / SessionStorage**

* ~5MB의 용량을 가진다.

* 동기 API로 메인 스레드의 블로킹을 한다.

* 문자열만 저장이 가능하며, 인덱싱 및 검색이 불가하다. (별도 로직 필요)

브라우저에서 제공하는 기존 로컬 저장소들은 설정 값을 저장하는 저장소 수준이지, DB 개념으로 사용하기에는 무리가 있었다. 2008 ~ 2012년 Gmail, Google Docs, Facebook 등의 웹 서비스들이 급부상되면서 수천수만 건의 데이터가 저장되어야하고 오프라인에서도 동작을 해야했다.

또 빠른 검색이 필요하며 UI 멈춤 없이 비동기 처리가 가능해야했기에 브라우저 자체에서 DB가 필요하다고 느끼게 되었고, 기존 브라우저의 로컬 저장소로는 해결이 되지 않던 문제를 IndexedDB를 정의하며 해결하고자 했던 것이다.

> **IndexedDB의 초기 설계 목표는 무엇이었을까?**

* 비동기 API로 메인스레드 블로킹을 최소화한다.

* 대용량 저장이 가능해야한다. (수백MB ~ 수 GB)

* 객체 형태 그대로 저장할 수 있도록 설계

* 인덱싱 및 검색이 가능해야한다.

* 트랜잭션을 지원한다.

* 브라우저 오프라인 환경을 우선적으로 지원한다. (오프라인 퍼스트)

* 단, 여기서 IndexedDB는 서버 DB를 대체하려는 것이 아닌 네트워크 없이도 웹 앱이 살아있게 하고자하는 철학을 가지고 있다. (인증, 보안 데이터가 아닌 캐시 및 오프라인 데이터 제공)

IndexedDB는 브라우저 자체의 DB라고 했다, 브라우저에서 사용하는 DB는 SQL이 아닌 NoSQL을 사용한다. 그 이유는 웹 데이터는 유연해야하기 때문에 스키마를 강제하지 않으며, 로컬스토리지와 같이 직렬화를 하지 않고 객체 그대로 저장하고 싶었다. 또 브라우저 구현을 단순화시키며, JS 객체 모델과 자연스럽게 맞추고자했던 포인트들이 있었기에 IndexedDB는 NoSQL을 채택하여 Key-Value + Object Store 구조를 가지게 되었다.

## Native IndexedDB 사용해보기

IndexedDB는 항상 DB 오픈 → Object Store 생성 (최초 1번) → Transaction 시작 → 읽기 / 쓰기 순서로 진행된다. 실무에서는 idb 라는 라이브러리를 사용한다고 하지만, 순수 IndexedDB도 어떤 방식으로 동작하는지 파악해야한다.

### 1. DB 오픈

`version` 이 변경되면 `onupgradeneeded` 실행시킨다. 이 안에서 테이블(ObjectStore)을 생성한다.

> **IndexedDB의 Version이란?**

IndexedDB에서 version 은 DB 스키마의 버전을 의미하며, 데이터 구조 변경의 이력 관리용이라고 생각하면 된다. IndexedDB는 한번 만들어진 ObjectStore를 그냥 아무때나 수정할 수 없으며, onupgradeneeded (버전이 변경되었을 때 호출) 안에서만 변경이 가능하다.

Version의 경우, 만약 이미 브라우저 상에 존재하는 DB의 인덱스 구조가 바뀌는 것과 같은 상황이 발생했을 때 업데이트를 해주어야하며 업데이트를 해주지 않을 경우 **이미 기존 DB 구조를 사용하고 있는 사용자들에게는 프로덕션 에러가 발생**할 것이다. 그래서 구조가 변경되면 버전 업데이트는 정말 중요하게 작용한다.

단, 아직 프로덕션 환경으로 배포되지 않고 개발 중인 상태라면 DB 삭제 후 다시 개발을 진행하면 된다.

* "app" : DB 이름

* 1 : 스키마 버전

* 반환 값은 DB가 아니라 `IDBOpenDBRequest`

```javascript
const request = indexedDB.open('app', 1);
```

### 2. 스키마 정의

* `ObjectStore` · `index` 생성 및 변경은 이 과정에서만 가능하다.

```javascript
request.onupgradeneeded = (e) => {
const db = e.target.result;

// ObjectStore 생성 (테이블)
const store = db.createObjectStore('post', { keyPath: 'id' });

// 인덱스 생성
store.createIndex('by_title', 'title');
}
```

### 3. DB 오픈 완료

* `db` 는 `IDBDatabase` 인스턴스를 의미한다.

* 읽기 및 쓰기가 가능하다.

```javascript
let db;

request.onsuccess = () => {
db = request.result;
};
```

### 4. 트랜잭션 시작

* `IndexedDB`의 모든 CRUD는 트랜잭션 안에서만 가능하다.

* 트랜잭션 메서드는 `"readonly"` or `"readwrite"`

```javascript
const tx = db.transaction("posts", "readwrite");
const store = tx.objectStore('post');
```

### 5. 데이터 저장 (add / put)

* add → 중복 key가 존재하면 적용되지 않는다.

* put → 중복 key가 존재하면 update 되고, 없으면 Insert 된다. (실무에서는 보통 put 방식을 사용한다고 한다)

```javascript
store.add({
id: 1,
title: "Hello"
});
```

### 6. 데이터 조회 (get)

* 모든 결과는 이벤트로 받으며, return 값은 존재하지 않는다.

```javascript
const getRequest = store.get(1);
getRequest.onsuccess = () => {
console.log(getRequest.result);
};
```

### 7. 전체 조회 (cursor)

* `IndexedDB`는 대량 데이터 전제이며, `getAll()`도 존재하지만 `cursor`가 기본 설계로 이루어져있다.

```javascript
const cursorReq = store.openCursor();

cursorReq.onsuccess = (e) => {
const cursor = e.target.result;
if (cursor) {
console.log(cursor.value);
cursor.continue();
}
}
```

### 8. 인덱스 조회

* 인덱스가 존재하지 않으면 `name == "Kim"` 과 같은 조건 검색을 하기 위해 풀 스캔을 해야하지만, 인덱스 내부에 자동으로 트리구조로 빠른 loopup을 제공할 수 있다.

```javascript
const index = store.index('by_title'); // 2.스키마 정의 부분 확인
const req = index.get('title');

req.onsuccess = () => {
console.log(req.result);
};
```

### 9. 트랜잭션 완료 및 실패

* 하나라도 실패하게 되면 전체를 롤백하며 DB의 일관성을 보장해준다.

```javascript
const tx = db.transaction("posts", "readwrite");

tx.oncomplete = () => {
console.log("트랜잭션 완료");
}

tx.onerror = () => {
console.error("트랜잭션 실패");
}
```

사실 indexedDB를 들여다보았을 때, 실제로 개발자들은 원본 IndexedDB의 메서드보다는 NPM 패키지인 idb 를 많이 사용한다고 한다. 그 이유는 **아래와 같이** indexedDB의 중첩 로직과 이벤트 지옥으로 인해 코드의 양과 가독성이 현저히 떨어지기 때문이다.

```javascript
request.onsuccess = () => {
const tx = db.transaction("posts", "readwrite");
const store = tx.objectStore('posts");
const req = store.get(1);
req.onsuccess = () => { // 지옥
console.log(req.result);
}
};
```

`idb` 를 많이 사용한다길래, idb 부터 사용을 해보았는데 idb 는 Promise 기반으로 이루어져있다. 그렇다면 왜 `IndexedDB`는 `Promise`가 아니라 이벤트 기반으로 설계가 되었을까?

## IndexedDB가 이벤트 기반으로 설계된 이유

IndexedDB가 설계되었을 당시에는 Promise가 존재하지 않았기 때문에 브라우저 스레드를 절대 막지 않으면서 취소 및 진행 상태를 다뤄야했기 때문에 이벤트 기반으로 설계되었다고 한다.

Promise가 없고, Async - Await이 존재하지 않았으며, 별도의 스레드인 Web Worker 또한 현재만큼 안정적이기 않았기 때문에 당시에는 비동기를 구현하기 위해서는 이벤트 및 콜백이 유일한 선택지였다. 그래서 IndexedDB도 DOM 이벤트 모델을 그대로 차용하여 구현이 된 것이다.

IndexedDB는 모든 동작마다 성공, 실패, 차단 이벤트가 발생하기 때문에 Promise보다는 상태 머신에 가까우며, onupgradeneeded, onblocked, onsuccess, onerror와 같은 상태들을 하나의 결과만을 반환하는 Promise로는 표현하기 역부족이다.

하지만 IndexedDB 자체의 각 상태는 어플리케이션 비즈니스 로직의 문제가 아닌, DB 엔진의 라이프사이클 관리의 영역이기 때문에 일반적인 개발자가 매번 직접 관여할 필요가 없다. 대부분의 클라이언트 코드에서는 복잡성보다는 가독성과 효율성을 원하기 때문에, idb 라이브러리에서는 Promise UX를 통해 결과 값만을 도출하며 또 DB 오픈 과정도 훨씬 간소화된 것이다.

## NPM Package (idb) 사용해보기

idb는 IndexedDB 이벤트 기반의 API를 Promise 기반으로 변환해주며 트랜잭션, cursor, upgrade를 안전하게 감싸주는 역할을 한다. 또, 타입스크립트 친화적이기에 사용법도 네이티브 indexedDB보다 훨씬 간편하다.

### 1. DB 오픈

* openDB 메서드를 통해 Promise를 반환하며, 내부적으로는 [indexedDB.open](https://indexedDB.open), onupgradeneeded, onsuccess 까지의 라이프 사이클을 여기서 끝낸다.

```javascript
import { openDB } from 'idb';

export const dbPromise = openDB('app-db', 1, {
upgrade(db) {
db.createObjectStore('posts', { keyPath: 'id' });
}
});
```

### 2. DB 인스턴스 얻기

* db는 IDBDatabase 인스턴스를 지칭하며, 현재부터는 이벤트는 없으며 await 키워드만 사용해야한다.

```javascript
const db = await dbPromise;
```

### 3. CRUD

* 저장(insert, update)의 경우, put 메서드를 사용하며 내부적으로는 transaction 생성, store 접근, put 실행, 완료 대기까지의 과정을 진행한다.

```javascript
await db.put("posts", {
id: 1,
title: 'Hello'
});
```

* 조회의 경우에는 get 메서드와 관련 id 값을 통해 조회할 수 있다.

```javascript
const post = await db.get('posts', 1);
```

* 전체 조회의 경우에는 getAll 메서드를 통해 관련 테이블의 모든 데이터들을 조회할 수 있다, 이때도 id 값을 필요로한다.

```javascript
const posts = await db.getAll('posts');
```

* 삭제의 경우에는 delete 메서드와 id 값을 통해 삭제할 수 있다.

```javascript
await db.delete('posts', 1);
```

### 4. 트랜잭션 사용하기 (여러 작업들을 한번에 묶어 사용하기)

* 트랜잭션을 통해 원자성을 보장받을 수 있으며, 여러 작업들을 묶어 작업하기 때문에 중간 코드가 실패 시에 전체적으로 롤백된다.

```javascript
const tx = db.transaction('posts', 'readwrite');
const store = tx.objectStore('posts');

await store.put({ id: 1, title: 'A' });
await store.put({ id: 2, title : 'B' });

await tx.done() // 중요
```

### 5. 인덱스 사용하기

```javascript
// 인덱스 생성 (Upgrade 단계)
upgrade(db) {
const store = db.createObjectStore('posts', { keyPath: 'id' });
store.createIndex('by_title', 'title');
}

// 인덱스 조회
const post = await db.getFromIndex('posts', 'by_title', 'Hello');
```

### 6. cursor 사용하기 (대량 데이터 조회)

* 내부에서는 openCursor, cursor.continue, 이벤트 루프를 전부 감춰준다.

```javascript
for await (const cursor of db
.transaction("posts")
.store
.openCursor()) {
console.log(cursor.value);
}
```

## 백오피스에는 실제로 어떻게 로직을 담았을까?

실제로 백오피스 서비스에서는 에디터가 변경될 때마다 디바운스 처리와 IndexedDB에 저장을 하면서, 클라이언트 상에서 자동저장을 구현하고자 했다. 그래서, 관련하여 컴포저블을 구성하고 이 컴포저블을 가져다 관련 DB 비즈니스 로직들을 메인 로직에 삽입하는 방식으로 진행했다.

```javascript
// useContentsAutoSave.ts
import { openDB } from 'idb';

interface ErrorResponse {
    success: boolean,
    error: Object | null
}

export default function useContentsAutoSave() {
    const contentDB = async () => await openDB('content-db', 1, {
        upgrade(db) {
            db.createObjectStore('contents', { keyPath: 'id' });
        }
    });

    const saveContent = async (id: string, data: any): Promise<ErrorResponse> => {
        try {
            const db = await contentDB();
            await db.put('contents', { id, ...data });
            return { success: true, error: null }
        } catch (error) {
            return { success: false, error: {} }
        }
    };

    const loadContent = async (id: string) => {
        const db = await contentDB();
        return await db.get('contents', id);
    }

    const removeContent = async (id: string) => {
        try {
            const db = await contentDB();
            await db.delete('contents', id);
            return { success: true, error: null }
        } catch(error) {
            return { success: false, error: {} }
        }
    }

    return { contentDB, saveContent, removeContent, loadContent }
}
```

```javascript
// Form.vue (저장)

<script setup>
const { saveContent } = useContentsAutoSave();

// htmlContent는 디바운스에 걸려 3초 시간의 간격을 가지고 있다.
watch(() => props.htmlContent, async () => {
await saveMount('content', {
title: 'title',
contents: 'html-content',
contentType: 'content-type',
})
});
</script setup>
```

다른 브라우저 로컬 스토리지와 다르게 객체 그대로 전달되는 것을 확인할 수 있었으며, 값도 정상적으로 저장된 것을 확인할 수 있었다.

![Image](https://upload.cafenono.com/image/slashpagePost/20260129/235525_BLDRy2deRS3yNrllmh?q=80&s=1280x180&t=outside&f=webp)

데이터를 정상적으로 저장했다면, 데이터 로드는 아래와 같이 컴포저블의 일부 함수를 호출해 바로 불러와줄 수 있다.

```javascript
// Form.vue (로드)

<script setup>
const { loadContent } = useContentsAutoSave();

onMounted(() => {
const { title, contents } = await loadContent('content');
title.value = title;
contents.value = contents;
});
</script>
```

최근에 백오피스 서비스에 IndexedDB를 새롭게 도입하면서, 아직까지는 Safari의 시크릿 모드 미지원 등과 같은 단점들을 제외하고는 큰 이팩트있는 단점을 찾지 못해 실시간 동기화 작업의 경우에는 IndexedDB를 활용한 저장 기능들을 추가해보고 있다. 아무래도 다른 로컬스토리지의 경우에는 객체 형태를 직렬화하여 저장하고, 또 이 값을 가져올 때는 다시 원복하는 로직들을 추가해야하는 경우가 허다했는데 단순히 객체에서 값만 뽑아오는 형태로 구성되니 훨씬 개발이 편리했다.

현재는 자동저장 기능에 IndexedDB를 활용한 방법을 녹여보았지만, 추후에 더 좋은 방법을 경험하거나 생각하게 된다면 리팩토링으로 개선해보는 시간을 가져보며 현 상황에 맞는 좋은 방법들을 적용해보려고한다.
