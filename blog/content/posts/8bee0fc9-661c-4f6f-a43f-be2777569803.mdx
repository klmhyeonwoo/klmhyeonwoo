DOM을 조작하다 보면 분명히 코드는 간단한데, 스크롤 할 때마다 버벅이고, 애니메이션은 뚝뚝 끊긴다. 레이아웃 작업이 수백 밀리초를 잡아먹고 있는데, 이 원인은 바로 **레이아웃 스레싱(Layout Thrashing)**이다.

### 변경이 생길 때 브라우저가 거치는 단계 (픽셀 파이프라인)

초기 로드 이후, JS로 DOM이 변경될 때마다 브라우저는 아래 흐름을 다시 탄다.

```javascript
JavaScript → Style → Layout → Paint → Composite
                        ↑
                  여기서 문제가 생긴다
```

* **Style**: 변경된 요소에 어떤 CSS 규칙이 적용되는지 재계산 (DevTools에서는 "Recalculate Style"로 표시)

* **Layout**: 각 요소의 위치와 크기를 계산 (Reflow라고도 부른다)

* **Paint**: 픽셀을 채우는 단계

* **Composite**: 레이어를 합성

이 중에서 **Layout** 단계가 제일 비싸다. 요소 하나의 크기가 바뀌면, 연관된 모든 요소의 위치를 다시 계산해야 하기 때문이다. 브라우저는 JavaScript 실행 중에 발생하는 DOM 변경들을 즉시 반영하지 않는다. **일괄 처리(batch)**해서 한 번에 처리한다. **레이아웃 스레싱은 바로 이 배치 처리를 무력화할 때 발생한다.**

> **픽셀 파이프라인이란?**

브라우저 렌더링 파이프라인은 "페이지를 처음 만드는 과정" 이라면, 픽셀 파이프라인은 "만들어진 페이지를 또 다시 갱신하는 과정"을 의미한다. 픽셀 파이프라인은 무조건 변경될 때마다 전부 다 실행되는 것이 아닌 어떤 것을 변경했냐에 따라 순서가 달라진다.

width 변경 → Style → Layout → Paint → Composite\
color 변경 → Style → Paint → Composite\
transform → Style → Composite\
 (단, opacity, transform은 Style/Layout/Paint를 건너뛰고 Composite만 실행)

### 레이아웃 스레싱이 무엇일까?

**레이아웃 스레싱(Layout Thrashing)**은 JavaScript가 DOM의 기하학적 속성을 읽고 쓰는 작업을 번갈아 가면서 반복할 때 발생한다.

```javascript
// 레이아웃 스레싱 예제
const boxes = document.querySelectorAll('.box');

for (let i = 0; i < boxes.length; i++) {
  const width = boxes[i].offsetWidth;   // ← 읽기: Layout 강제 실행
  boxes[i].style.width = width + 10 + 'px'; // ← 쓰기: 레이아웃 무효화
}
// 다음 반복에서 다시 읽기 → Layout 또 강제 실행 → 무한 반복
```

왜 이게 문제냐면 ^,^ ..

1. `boxes[i].style.width`를 변경하면 브라우저는 레이아웃을 **무효(dirty)**로 표시한다

1. 다음 반복에서 `offsetWidth`를 읽으면, 레이아웃이 무효 상태이므로 브라우저는 정확한 값을 반환하기 위해 강제로 레이아웃을 다시 계산한다

1. 이걸 **Forced Synchronous Layout** 이라고 부른다

1. n개의 요소가 있으면 n번 레이아웃이 실행된다

100개 요소면 100번이다. 1000개면 1000번.

### 레이아웃을 강제하는 속성들

모든 DOM 읽기가 레이아웃을 강제하는 건 아니다. 기하학적 정보를 요구하는 속성들이 문제다.

```javascript
// 이 속성들을 읽으면 레이아웃이 강제 실행된다

// 크기/위치 관련
element.offsetWidth, element.offsetHeight
element.offsetTop, element.offsetLeft
element.offsetParent
element.clientWidth, element.clientHeight
element.clientTop, element.clientLeft
element.scrollWidth, element.scrollHeight
element.scrollTop, element.scrollLeft    // ← 읽기만 해도 강제 실행

// 좌표 관련
element.getBoundingClientRect()           // ← 자주 쓰이는 범인
element.getClientRects()

// 계산된 스타일
window.getComputedStyle(element)          // ← 이것도 해당됨

// 스크롤
window.scrollX, window.scrollY
window.innerWidth, window.innerHeight
```

반면 `[element.style.width](https://element.style.width)`처럼 설정된 인라인 스타일을 읽는 건 레이아웃을 강제하지 않는다.

실제 계산된 값이 아니라 인라인으로 지정된 문자열을 그대로 반환하기 때문이다.

### 실제로 얼마나 느려지나

DevTools의 Performance 탭을 열면 레이아웃 스레싱이 일어나는 구간에 경고 삼각형이 찍힌다.

```javascript
Before (레이아웃 스레싱 있음):
  Frame 1: 280ms  ← 16ms를 훌쩍 넘겨서 프레임 드롭
  Frame 2: 290ms
  Frame 3: 270ms
  → 초당 3~4 프레임 수준

After (수정 후):
  Frame 1: 8ms    ← 여유 있게 16ms 안에 처리
  Frame 2: 7ms
  Frame 3: 9ms
  → 매끄러운 60fps
```

60fps를 유지하려면 한 프레임에 16.67ms 안에 모든 처리가 끝나야 한다. 레이아웃 스레싱이 있으면 그 예산을 금방 초과한다.

### 읽기와 쓰기, 어떻게 분리해야 할까

핵심은 간단하다. **읽는 작업을 먼저 몰아서 하고, 쓰는 작업을 나중에 몰아서 한다.**

```javascript
// ✅ 읽기 먼저, 쓰기 나중에
const boxes = document.querySelectorAll('.box');
const widths = [];

// 1단계: 읽기만 한다
for (let i = 0; i < boxes.length; i++) {
  widths.push(boxes[i].offsetWidth);  // ← 레이아웃은 처음 한 번만 실행
}

// 2단계: 쓰기만 한다
for (let i = 0; i < boxes.length; i++) {
  boxes[i].style.width = widths[i] + 10 + 'px'; // ← 레이아웃 무효화만 함
}
// 브라우저가 다음 프레임에 레이아웃을 한 번만 실행
```

이렇게 하면 레이아웃 계산은 딱 한 번만 일어난다.

### requestAnimationFrame으로 시점 제어

읽기/쓰기 분리가 항상 한 함수 안에서 가능한 건 아니다. 복잡한 UI에서는 서로 다른 컴포넌트가 레이아웃 정보를 읽고 쓰는 경우가 많다.

이럴 때 `requestAnimationFrame`이 도움이 된다.

```javascript
// 쓰기 작업은 rAF로 다음 프레임으로 미룬다
function updateBox(element) {
  const width = element.offsetWidth; // ← 지금 당장 읽기

  requestAnimationFrame(() => {
    element.style.width = width + 10 + 'px'; // ← 다음 프레임에 쓰기
  });
}
```

브라우저는 rAF 콜백을 실행하기 직전에 레이아웃을 처리한다. 그 시점에 쓰기를 하면 다음 프레임에 한 번만 레이아웃이 실행된다.

### FastDOM — 읽기/쓰기 큐잉 라이브러리

규모가 커지면 수동으로 관리하기 힘들다. 이 문제를 체계적으로 해결하는 라이브러리가 **FastDOM**이다.

```javascript
import fastdom from 'fastdom';

// 읽기는 measure로
fastdom.measure(() => {
  const width = element.offsetWidth; // ← 읽기 큐에 쌓임

  // 쓰기는 mutate로
  fastdom.mutate(() => {
    element.style.width = width + 10 + 'px'; // ← 쓰기 큐에 쌓임
  });
});

// FastDOM이 알아서:
// 1. measure 콜백들을 모두 실행 (읽기)
// 2. mutate 콜백들을 모두 실행 (쓰기)
// 3. 레이아웃은 딱 한 번
```

내부적으로는 rAF를 사용해서 읽기 → 쓰기 순서를 보장한다.

### 비교: 상황별 선택 가이드

| 상황                      | 추천 방법                                   |
| ----------------------- | --------------------------------------- |
| 단순 루프에서 읽기/쓰기 반복        | 읽기 배열로 모아두고 쓰기 분리                       |
| 비동기 컴포넌트 간 DOM 접근       | `requestAnimationFrame` 사용              |
| 규모 있는 앱, 여러 곳에서 DOM 접근  | FastDOM 도입                              |
| React/Vue 같은 프레임워크 사용 중 | 프레임워크의 상태 관리를 통해 처리, 직접 DOM 접근은 최소화     |
| CSS만으로 해결 가능한 애니메이션     | `transform`, `opacity`로 레이아웃 건드리지 않게 처리 |

사실 React나 Vue를 쓴다면 레이아웃 스레싱을 직접 경험할 일이 많지 않다. Virtual DOM이 배치 처리를 대신해주기 때문이다. 근데 `useEffect` 안에서 `getBoundingClientRect()`를 읽고 상태를 업데이트하면 똑같은 문제가 생긴다.

### CSS로 레이아웃 자체를 피하는 방법

가장 좋은 해결책은 레이아웃을 아예 건드리지 않는 것이다.

```javascript
/* ❌ 레이아웃을 유발하는 속성 */
.box {
  transition: width 0.3s, height 0.3s, top 0.3s, left 0.3s;
}

/* ✅ Composite 단계만 사용하는 속성 */
.box {
  transition: transform 0.3s, opacity 0.3s;
  /* transform과 opacity는 레이아웃, 페인트를 건너뛴다 */
}
```

`transform`과 `opacity`는 GPU가 처리하는 Composite 단계에서만 동작한다. 레이아웃과 페인트를 건너뛰기 때문에 훨씬 빠르고, 레이아웃 스레싱의 영향도 받지 않는다.

위치 이동 애니메이션은 `left/top` 대신 `transform: translate()`를 쓰는 게 좋다.

```javascript
// ❌ 레이아웃 유발
element.style.left = x + 'px';
element.style.top = y + 'px';

// ✅ Composite만 사용
element.style.transform = `translate(${x}px, ${y}px)`;
```

### will-change로 레이어 승격시키기

자주 애니메이션되는 요소는 `will-change`로 GPU 레이어로 미리 승격시킬 수 있다.

```javascript
.animated-box {
  will-change: transform;   /* ← 이 요소는 transform이 자주 바뀔 거라고 힌트 */
}
```

브라우저가 미리 레이어를 생성해두기 때문에 애니메이션 시작 시 레이아웃 계산 없이 바로 처리한다.

근데 남발하면 메모리를 많이 잡아먹는다. 정말 자주 바뀌는 요소에만 쓰는 게 좋다.

결국 레이아웃 스레싱은 **브라우저의 최적화 전략을 모르고 방해하는 것**이다.

브라우저는 배치 처리로 레이아웃 횟수를 최소화한다. 읽기/쓰기를 번갈아 반복하면 그 최적화가 매번 무효화된다.

해결은 단순하다. 읽기는 읽기끼리, 쓰기는 쓰기끼리 묶는 것이 기본이다. 가능하면 `transform`과 `opacity`를 사용해서 레이아웃 자체를 건드리지 않는 것이 좋다. 복잡해지면 FastDOM이나 rAF로 시점을 제어하면 된다.
