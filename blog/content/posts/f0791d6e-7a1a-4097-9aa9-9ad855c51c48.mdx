Scion에 대한 소식을 보고 문득 궁금해졌다. AI가 코드를 많이 작성한다고 해서, 그동안 잘 사용하던 Git을 바꿔야 할 정도가 될 수 있을까? 처음에는 저장소가 커지면서 생기는 속도 문제라고 생각하기 쉬운데, Anthropic의 설명을 읽어보면 단순히 Git 명령어를 빠르게 만드는 것과는 조금 다른 이야기이다.

Scion은 Anthropic이 자체적으로 만든 버전 관리 시스템이다. 사람이 오프라인에서도 작업할 수 있는 Git의 전제 대신, 대부분의 클라이언트가 항상 온라인인 에이전트와 자동화 작업이라는 전제에서 출발한다. 어떤 차이가 생기는지 한번 정리해보려고 한다.

이 글은 2026년 10월 13일 공개된 Anthropic의 엔지니어링 글을 바탕으로 작성했다. Scion을 직접 사용해본 후기는 아니며, (사실 도입할 이유가 없기도 하고, 어떠한 것인지 알아보기 위한 목적이 제일 크다 👀) 아래 성능 수치는 Anthropic이 공개한 내부 환경의 측정 결과이다.

## 코드를 작성하는 속도보다, 코드를 받아들이는 속도가 느려진다면

Anthropic에 따르면 하루에 병합되는 코드 변경은 2026년 5월 평균 약 2,500건에서 9월에는 3만 건 이상으로 늘어났다. 코드 작성이 빨라지니, 그 코드를 저장하고 가져오고 테스트하는 개발 인프라가 다음 병목이 된 것이다.

당시 모노레포는 main 브랜치의 이력만 거의 100GB였고, 압축한 작업 사본도 25GB를 넘었다. CI에서만 하루 약 2,500만 번의 체크아웃이 발생했다. 개발 환경이나 에이전트 샌드박스, 연구 작업은 이 숫자에 포함되지 않는다.

이 규모에서 데이터를 단순하게 매번 가져온다고 가정하면 하루 트래픽이 600PB를 넘는다고 한다. 여기서 주의할 점은 실제로 매일 600PB를 전송했다는 뜻이 아니라, 단순하게 가져오는 방식을 적용했을 때의 추정치라는 점이다.

그렇다면 필요한 부분만 가져오면 되지 않을까? 실제로 Anthropic도 shallow clone, sparse checkout, 필요한 객체를 원격에서 가져오는 방식, 내부 미러와 스냅샷까지 활용했다고 한다. 최대 수백 개의 Git 미러를 운영했지만, 변경이 계속 쌓이면서 최신 상태를 유지하고 부분 복제 환경에서 diff나 blame을 정상적으로 제공하는 운영 부담도 커졌다.

## Git이 가진 장점이, 이 환경에서는 비용이 될 수 있다

일반적인 Git clone은 로컬에 독립적으로 동작하는 저장소를 만든다. 네트워크가 끊겨도 커밋을 만들거나 이력을 확인하고, 변경 내용을 비교할 수 있다. 각 개발자가 서버 없이도 작업할 수 있다는 점은 Git의 중요한 장점이다.

물론 모든 Git 클라이언트가 반드시 모든 데이터를 받아야 하는 것은 아니다. 앞서 언급한 부분 복제나 얕은 복제 같은 기능도 존재한다. Scion이 해결하려던 문제는 이런 기능이 없다는 것이 아니라, Anthropic의 규모에서 여러 기능과 미러를 조합해 운영하는 비용이 커졌다는 데 있다.

반대로 Anthropic의 클라이언트 대부분은 어차피 네트워크에 연결되어 있는 에이전트와 자동화 작업이었다. 그렇다면 각 클라이언트가 독립적인 저장소의 역할을 모두 수행해야 할까? Scion은 이 역할을 서버 쪽으로 옮기는 방식을 선택했다.

## 커밋과 리베이스를 서버에서 처리하기

Scion에서는 서버가 커밋 생성, 병합, 리베이스, 파일 이력 및 blame 조회를 처리한다. 클라이언트는 크기가 제한된 객체 캐시를 유지하고, 작업 파일을 디스크에 배치하며 파일 변경을 감시하는 역할을 맡는다.

Git에서는 로컬에서 커밋을 만든 뒤 push로 공유하지만, Scion은 커밋 자체가 서버에서 만들어지므로 별도로 push할 필요가 없다. 그렇다고 커밋을 만드는 즉시 main에 병합되거나 배포된다는 뜻은 아니다. 커밋 생성과 리뷰 및 병합은 구분해서 봐야 한다.

또 하나의 차이점은 저장소를 반드시 로컬에 펼쳐놓을 필요가 없다는 점이다. 예를 들어 CI 작업이 두 변경 사이의 diff만 필요하다면, 파일 전체를 체크아웃하지 않고 서버 API로 결과를 요청할 수 있다. 파일을 수정하는 일부 작업도 API만으로 수행할 수 있다.

다만 서버 연결을 전제로 한다는 것은 그만큼 네트워크와 서버 가용성에 의존한다는 의미이기도 하다. 오프라인에서도 독립적으로 작업할 수 있는 Git의 장점을 그대로 유지하면서 모든 비용만 줄인 구조는 아니다.

## Changeset에는 무엇이 들어갈까?

Scion의 작업 단위는 changeset이다. Git 커밋이 트리 객체를 가리키는 것과 달리, changeset은 첫 번째 부모를 기준으로 어떤 파일이 바뀌었는지와 해당 파일 내용의 주소를 기록한다. 파일 내용은 압축되어 blob storage에 저장되고, 내용으로부터 정해지는 주소로 참조한다.

여기서 변경된 파일 목록을 저장한다는 것이 파일 안의 줄 단위 패치만 저장한다는 의미는 아니다. 변경된 파일과 그 파일 내용의 참조를 기록하는 구조로 이해하면 된다. 커밋 생성 비용이 저장소 전체 크기보다 실제 변경 크기에 비례하도록 하는 것이 목표이다.

그러면 변경 목록만 가지고 특정 줄을 누가 마지막으로 수정했는지 바로 알 수 있을까? 이런 조회를 빠르게 처리하기 위해 Scion은 별도의 파생 데이터를 만든다. 파일별 blame과 경로 이력, 커밋 그래프를 탐색하는 자료구조 등이 여기에 해당한다.

즉, 변경을 기록하는 데이터와 조회를 빠르게 하기 위한 데이터를 나누는 것이다. 파생 데이터는 종류에 따라 미리 계산할 수도 있고, 필요할 때 계산할 수도 있다. 클라이언트가 내부 자료구조를 알 필요가 없기 때문에 서버의 조회 구조를 개선해도 클라이언트를 함께 바꾸지 않아도 된다.

## 같은 파일을 계속 가져오지 않도록 캐시하기

Scion의 scn 클라이언트는 필요한 tree와 blob 객체를 확인하고, 로컬에 없는 객체만 요청한다. 여기서 tree는 디렉터리 구조를, blob은 파일 내용을 표현하는 객체로 생각하면 된다. 원하지 않는 디렉터리의 객체는 요청하지 않으므로 sparse checkout이 자연스럽게 동작하고, 실제로 읽는 파일만 디스크에 만드는 가상화된 체크아웃도 지원한다.

콘텐츠 주소로 식별되는 객체는 저장된 뒤 내용이 변하지 않는다. 같은 주소의 데이터를 다른 서버가 캐시하고 있어도, 최신 버전인지 매번 확인할 필요가 없다는 뜻이다. 이 성질을 활용해 여러 단계의 캐시에서 요청을 처리한다.

먼저 같은 노드의 작업들이 scion-daemon을 통해 객체를 공유한다. 여기에 없으면 해당 리전의 scion-cache에 요청하고, 그곳에도 없다면 scion-servers가 Spanner나 클라우드 스토리지에서 데이터를 가져온다. 매번 각 작업이 별도의 저장소를 내려받고 관리하는 부담을 줄일 수 있다.

각 캐시 계층의 적중률은 99%를 넘는다고 한다. 다만 캐시 서버를 많이 두는 것만이 전부는 아니다. Anthropic은 리전 캐시 장애가 원본 서버로 요청을 몰아 전체 장애로 번지지 않도록 계층 구조를 엄격하게 유지한다고 설명한다.

## 어느 정도 개선되었을까?

Anthropic이 공개한 결과에서 기존 Git 미러 인프라 대비 CPU와 메모리 요구량은 200분의 1 수준으로 줄었다. 이 수치는 모든 Git 명령어가 200배 빨라졌다는 의미가 아니라, 해당 미러 인프라와 비교한 자원 요구량의 변화이다.

또 CI와 연구 작업의 체크아웃은 기존의 분 단위에서 초 단위로 줄었고, CI에서만 CPU 처리 여력 25%를 확보했다고 한다. 저장소 데이터를 가져오고 유지하는 비용이 줄어든 결과이다.

물론 이 숫자를 일반적인 프론트엔드 프로젝트에 그대로 적용하면 안 된다. 저장소의 크기, 체크아웃 횟수, 캐시 공유 정도가 전혀 다르기 때문이다. 작은 저장소에서 Git 명령어를 실행하는 경우와 Anthropic의 모노레포를 같은 조건으로 비교할 수는 없다.

## 버전 관리만 바꾸면 끝나는 문제일까?

Scion과 함께 코드 리뷰 도구인 Antique, 코드 검색과 접근 제어 등도 구축되었다. 7명의 팀이 관련 시스템을 만들고 모노레포를 이전하는 데 5개월이 걸렸다고 한다. 새로운 CLI 하나를 설치해서 Git 명령어만 바꾸는 종류의 도입은 아니었던 것이다.

흥미로운 점은 테스트와 병합 방식까지 다시 고민했다는 것이다. 테스트가 실행되는 동안 수백, 수천 개의 변경이 병합된다면, 테스트를 시작할 때의 코드와 끝났을 때의 main은 상당히 달라질 수 있다.

Anthropic은 저장소 전체를 잠그는 병합 대기열 대신 병합 후와 배포 전 자동 테스트에 투자했다고 설명한다. 이것도 테스트를 하지 않고 코드를 내보낸다는 뜻은 아니다. 변경량이 커졌을 때 어떤 시점에서 검증할지에 대한 선택이고, 동시 변경 사이의 충돌 가능성이 사라지는 것도 아니다.

## 그러면 우리도 Git 대신 Scion을 사용해야 할까?

Anthropic은 Scion이 일반적인 용도의 Git 대체재로 적합하지 않다고 명시한다. 수만 명의 엔지니어나 대량의 코드를 작성하는 에이전트가 사용하는 초대형 모노레포에 맞춘 설계이며, 자체 코드 리뷰와 검색, CI까지 필요하기 때문이다. 내부에서 사용할 수 있는 AI 토큰의 규모도 다른 조직이 현실적으로 감당하려는 수준과 다르다고 설명한다.

따라서 공개된 글은 누구나 바로 설치해서 사용할 수 있는 범용 제품의 안내라기보다, 특수한 규모의 문제를 어떻게 풀었는지 공유한 사례로 읽는 편이 맞다. Anthropic도 이 경험을 Git 서버의 구조나 API, 객체 전송 방식 개선에 적용할 수 있기를 기대하고 있다.

Scion에서 흥미로웠던 부분은 Git을 버렸다는 사실보다, 클라이언트가 정말로 어떤 일을 해야 하는지 다시 나누었다는 점이다. 파일이 필요하지 않은 작업에는 파일을 내려주지 않고, 같은 데이터는 공유하며, 조회에 필요한 계산은 서버에서 처리한다.

AI가 코드를 더 빠르게 작성하면 개발 과정 전체도 같은 비율로 빨라질 거라고 생각하기 쉽다. 하지만 그 뒤에서 변경을 받아들이고 검증하는 과정이 따라가지 못하면, 병목은 그쪽으로 옮겨갈 수 있다. Scion은 그다음 병목이 실제로 어떤 모습으로 나타날 수 있는지 보여주는 사례인 것 같다.
