백오피스 개발을 진행할 때 대량의 데이터를 다루는 대시보드 형태와 리스트 형태를 많이 다루다보니 리스트에 여러 페이지네이션 뿐만 아니라 검색 필터조건들이 정말 많은 편이다. 그 과정에서 데이터 패칭 시에 서버 데이터의 상태 관리를 위한 tanstack query를 사용하고 있다.

tanstack query에서는 해당 데이터의 재패치를 하기 위해 의존성으로 ` queryKey `라는 값을 설정하게 되는데, 이 ` queryKey `에 설정된 데이터들이 바뀌게 되면 데이터의 재패치가 일어난다. 그런데, 아래와 같은 코드가 있다고 가정해보자. 정말 신기한 일이 일어난다.

```javascript
// Vue3 Watch
watch([
  searchDate,
  searchCustomerType,
  searchCustomer,
  searchUserName,
  searchFeedbackStatus,
  searchPageRows,
], () => {
  currentPage.value = 1;
}, { deep: true });
```

```javascript
// Tanstack Data Fetch
...
queryKey: () => ({
	computed(() => currentPage.value
	computed(() => searchDate.value
  ...
})
```

React를 본래 메인 기술 스택을 하던 사람이라면 위의 코드에서 이상한 점을 느꼈을 수도 있다. 바로 ` queryKey `에 의존성으로 들어간 값을 ` watch `에서 다른 값들이 변할 때 ` currentPage `라는 값을 강제로 바꿔주면서 데이터가 여러 번 재패치가 일어날 수도 있다. 하지만 현실은 그렇지 않다. 단 1번의 패칭만이 일어나게 된다.

## Vue의 배치 업데이트

여기서의 핵심은 ` queryKey `의 변경이 값을 대입하는 즉시 요청을 보내는 방식이 아니다. Vue의 반응성 업데이트가 한번에 모인뒤 최종 상태를 보고 처리된다는 점이다. 그래서 의존성에 들어간 값을 아무리 바꿔도 실제로 패치는 한번 실행이 된다.

예를 들어 아래와 같이 3번째 페이지에 도달했을 때 검색 필터를 바꾸게 되면 올바른 검색 결과를 위해 1번째 페이지로 이동을 해줘야한다, 이럴 때와 같이 동기 실행 흐름을 확인할 수 있다. 

```text
searchUserName = ‘홍길동‘
→ 기존 watch 의존성 안에 searchUserName이 존재하기 때문에 watch 예약
→ useQuery의 queryKey 갱신도 예약

watch 실행
→ currentPage = 1
→ queryKey 갱신이 다시 예약됨

반응성 큐 flush
→ 최종 queryKey: [‘…’, ‘홍길동’, 1]
→ 이 키로 1회 조회됨
```

Vue는 같은 tick 안에서 동일한 watcher/effect를 여러 번 실행하지 않도록 묶는다. 그래서 “새 필터 + 세번째 페이지” 라는 중간 키는 실제 요청으로 이어지기 전에, “새 필터 + 첫 번째 페이지”로 덮이게 된다. 반대로 아래처럼 페이지 변경을 다음 tick으로 미루번 2번 호출될 수 있다.

```javascript
watch(searchUserName, async () => {
	await nextTick();
	currentPage.value = 1;
})
```

이렇게 다음 tick으로 먼저 미룬 경우에는, 우리가 처음에 예상하던 바처럼 먼저 검색어 변경과 세번째 페이지로 한번 조회되고, 다음 tick에서 검색어 변경과 첫 번째 페이지로 두번 조회가 될 수 있다. 현재 구현은 await이나 setTimeout 없이 동기적으로 페이지를 바꾸므로, useQuery가 최종 키만 받아 보통 한 번 요청하는 구조를 가진다.

## 반면 React에서는?

React도 queryKey에 의존성을 넣어놓으면 값이 변경될 때 재패치가 일어나는 원리는 같지만, useEffect 안에서 의존성 값을 바꿔주는 경우에는 2번 실행된다는 Vue와의 동작 차이점을 가지고 있다.

```javascript
const [page, setPage] = useState(3);
const [keyword, seyKeyword] = useState(‘’);

…
useQuery({
	queryKey: [‘chat-list’, keyword, page],
	queryFn: fetchChats
});

useEffect(() => {
	setPage(1);
}. [keyword])
```

위와 같이 코드를 구성했다고 가정하고, 검색어 변경이 일어났을 때 검색어 변경 동작에 대한 렌더가 먼저 커밋되고, useQuery의 keyword + 기존 page로 요청한다. 이후 effect가 실행되어 page = 1에 대한 렌더 요청이 한번 더 일어나게 된다. 그래서 React에서는 검색 이벤트와 함께 이벤트로 명시적인 갱신처리를 하는 것이 안전하다.

```javascript
const onChangeKeyword = (value: string) => {
	setKeyword(value);
	setPage(1);
}
```

## useEffect와 watch는 왜 다를까?

Vue가 React와 동작이 다른 점은, Vue의 watch는 기본적으로 렌더 전(pre-flush)에 실행되어, 이 React의 useEffect보다 “상태를 먼저 정리하는” 흐름에 가깝기에 한번에 처리할 수 있는 것이다.

여기서 중요한 점은 페이지를 1번으로 바꾸는 코드가 어느 업데이트 단계에서 실행되느냐에 대한 차이이다. 현재 Vue 코드는 watch를 기반으로 업데이트가 되는 것을 확인할 수 있었다.

```javascript
watch([…filters], () => {
	currentPage.value = 1;
});
```

Vue의 watch의 기본 실행 시점은 flush: ‘pre’, 즉 화면 렌더 및 반응성 작업 전에 실행되는 큐이다. 게다가 이 watch가 useQuery보다 먼저 등록되기 때문에 한번의 반응성 flush 안에서 아래와 같은 작업을 거쳐 1번 실행되게 되는 것이다.

```text
필터 변경
→ 페이지 초기화 watch 실행
→ queryKey가 최종 값이 새 필터, 1페이지가 됨
→ Vue Query가 최종 키를 보고 조회 
```

반면 React에서의 useEffect는 렌더가 커밋된 다음 실행이 된다.

```javascript
useEffect(() => {
	setPage(1);
}, [keyword]);
```

```text
keyword 변경
→ 렌더 커밋 : 새 keyword + 기존 세번째 페이지 조회
→ React Query가 해당 키로 조회 가능 (1번 실행)
→ useEffect 실행
→ page를 1로 변경
→ 다시 렌더 : 새 keyword + 첫번째 페이지 조회 (2번 실행)
→ 다시 조회 가능
```

즉 두 프레임워크의 차이점을 정리해면 Vue의 watch는 렌더 전 상태 정리를, useEffect는 렌더 후 부수 효과라는 실행 순서에 있다.

<details open>
<summary> React에서는 렌더 전 상태 정리를 하지 못할까?</summary>

React에서는 ` useLayoutEffect `라는 훅이 존재한다. React가 DOM 변경을 반영한 직후 브라우저에 화면을 그릴 때의 작업인 ` paint ` 작업 전에 **동기적으로** 실행하는 훅이다.

```text
렌더 계산
→ DOM 반영 (commit)
→ useLayoutEffect
→ 화면 표시 (paint)
→ useEffect
```

보통은 useEffect를 사용하고, DOM을 측정하거나 화면이 보이기 전에 DOM 위치를 보정해야 할 경우에만 사용한다. 그 이유는 이 훅은 동기 작업을 진행하기 때문에 내부 작업이 마칠 때까지 화면 표시를 막는다는 것이다. 네트워크 요청, 데이터 조회, 일반 상태 동기화, 구독 등록에는 useEffect를 사용해야한다.

위 내용에서 Vue의 watch는 useQuery보다 먼저 실행이 되었고, 이로 인해 하나의 반응성 flush에서 안에서 합쳐진다. 반면, React ` useLayoutEffect `는 paint 전에 실행될 뿐 useQuery가 실행되는 render보다 먼저 실행되지 않는다. 그래서 ` useLayoutEffect `에서 currentPage = 1 값을 넣으면 watch와 똑같이 되는거 아닐까? 라는 생각은 잘못된 생각일 수 있다.

```text
필터 변경
→ render: 새 필터 + 세번째 페이지
  ㄴ useQuery도 이 시점의 queryKey를 동시에 받음
→ commit
→ useLayoutEffect 실행
→ setPage(1)
→ 두 번째 render: 새 필터 + 첫번째 페이지
  ㄴ useQuery가 두번째 queryKey를 받음
→ paint
```

\* Vue watch의 경우 렌더 전 상태 정리 뿐만 아니라 속성을 주어 렌더 후 부수효과처럼 사용도 가능하니 참고하자. 

> 두 프레임워크는 애초에 다르게 설계되었다. Vue는 기본적으로 Proxy 기반의 반응성 그래프 중심이기 때문에 스케쥴러 단계들을 선택해서 처리가 가능하다. 반면 React는 render 과정 자체가 순수해야한다는 원칙이 강하기 때문에 렌더 결과의 스냅샷 중심으로 이루어져있다.

## 부록 : React에서 예외적으로 허용하는 보정 패턴

위의 내용들을 기반으로 렌더 함수 내부에서 처리를 하는 것보다는 이벤트 안에서 명시적으로 처리하는 것이 안전하다는 것을 알았다. 그 밖에 다른 React가 예외적으로 허용하는 “렌더 중 조건부 상태 보정” 패턴이다. 이전 props · state를 저장해두고, 값이 달라졌을 때만 렌더 함수 안에서 상태를 바꾸는 방식이다.

```typescript
function ChatList({ keyword }: { keyword: string }) {
	const [previousKeyword, setPreviousKeyword] = useState(keyword);
	const [page, setPage] = useState(1);

	if (keyword !== previousKeyword) {
		setPreviousKeyword(keyword);
		setPage(1);
	}	
	
	// 여기서 page는 다시 렌더될 때 첫 번째 페이지 값을 가진다.
	return <List keyword={keyword} page={page}/>;
}
```

여기서 중요한 점은 조건이 없으면 무한 렌더가 될 수 있다는 점을 주의해야한다. useEffect처럼 커미션 후에 상태를 고치는 것이 아니라 커밋 전에 렌더를 한 번 재시도한다는 점이 다르다.

```text
keyword props 변경
→ 이전 page를 가진 상태로 컴포넌트 함수 실행
→ keyword가 이전이랑 다른지 검사
→ setPage(1)
→ React가 이번 렌더 결과를 버리고 즉시 다시 렌더
→ 새 keyword + 첫 번째 페이지로 렌더 결과 커밋
```

keyword 대신 매 렌더마다 새로 만들어지는 객체를 비교 대상으로 쓰면, 계속 “변경됨” 으로 판단할 수 있어 위험하다. 이 패턴의 경우 부모 props 변경처럼 이벤트 핸들러를 직접 제어할 수 없을 때 한정하여 유용하다. 검색 입력처럼 변경 이벤트를 직접 처리할 수 있는 현재 경우라면 이벤트에서 처리하는 것이 명확하고 좋은 방법이라 굳이 사용할 필요는 없지만, 알아두면 좋을 것 같다.
